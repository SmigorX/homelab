# Uptime Kuma

Argo CD deploys service monitoring through
`argocd/apps/workloads/uptime-kuma.yaml`, published at
`uptime.k8s.internal.smigorx.eu`.

## Authentication

Uptime Kuma has no OIDC of its own — [louislam/uptime-kuma#5589][issue] is
still open — so unlike every other application here it is not an Authentik
OAuth2 client. It sits behind **forward auth** instead: Traefik asks Authentik
about every request before it reaches the app, and the app itself never learns
that SSO happened.

[issue]: https://github.com/louislam/uptime-kuma/issues/5589

This is the first `Middleware` in this repo, and the first proxy provider in
`authentik/manifests/blueprints.yaml`. Four pieces have to agree:

| Piece | Where |
| --- | --- |
| Proxy provider + application + outpost assignment | `authentik/manifests/blueprints.yaml`, key `uptime-kuma.yaml` |
| `forwardAuth` middleware | `manifests/middleware.yaml` |
| Router annotation pointing at it | `manifests/ingress.yaml` |
| Group allow-list | `authentik/manifests/blueprints.yaml`, same key |

### Who gets in

Two groups are bound to the application: `guests` and `authentik Admins`. The
application's policy engine mode is `any`, so they read as *or* — membership
of either is enough.

Those bindings are what makes access a decision. An Authentik application with
no bindings at all is reachable by **every** authenticated user, which is what
this was until they were added: forward auth proved that somebody had logged
in, never that they were entitled to Uptime Kuma. So the first binding
*narrowed* access rather than widening it, and a set of bindings that names no
group of yours locks you out along with everyone else. Admins are listed
explicitly for that reason — being a superuser grants no implicit pass.

`guests` and its membership are declared in the blueprint, so a member added
through the web interface is dropped on the next reconcile; new guests belong
in that list. The accounts themselves stay hand-made, since declaring one
would put a password in Git.

### Why domain level, not single application

The provider runs in `forward_domain` mode. `forward_single` is the more
obvious choice, but it requires `/outpost.goauthentik.io/*` to be routable on
the application's *own* host, which across namespaces means an `ExternalName`
Service — and k3s starts Traefik without
`--providers.kubernetescrd.allowExternalNameServices`, so that route would
silently never work. Domain level keeps the whole login round trip on
`auth.k8s.internal.smigorx.eu`, which already exists, and sets one cookie for
the entire `k8s.internal.smigorx.eu` zone.

The useful side effect is that none of this is Uptime Kuma specific. Another
app with no SSO of its own needs only a copy of the Middleware in its namespace
and its provider added to the same embedded outpost — no new Authentik host, no
new outpost Deployment.

### This fails open

`traefik.ingress.kubernetes.io/router.middlewares` takes a
`<namespace>-<name>@kubernetescrd` string that nothing validates. If the
namespace is renamed, the middleware is renamed, or the annotation is dropped,
Traefik does not error — it serves Uptime Kuma **with no authentication at
all**. Worth an actual check after any rename:

    curl -sk -o /dev/null -w '%{http_code}\n' https://uptime.k8s.internal.smigorx.eu/

A logged-out browser and a bare `curl` should both be redirected to Authentik,
never answered with the dashboard.

## Storage

`uptime-kuma-data` (2Gi, `local-path-core`) holds the SQLite database with all
monitors, history and settings. `strategy: Recreate` because SQLite does not
tolerate two writers, and the volume is ReadWriteOnce regardless.

## Secrets

None. Proxy providers get their client secret generated by Authentik, so unlike
the OAuth2 entries there is nothing to keep in step between
`authentik/values.yaml` and Vault. The Uptime Kuma admin account is created in
the UI on first run.

## First run

Open `https://uptime.k8s.internal.smigorx.eu`. Authentik authenticates you
first, then Uptime Kuma shows its own setup screen and asks for an admin user
and password — the two logins are independent, and at this point you are
holding both.

Note that Uptime Kuma has a single account rather than one per person, so
letting a second individual in means either sharing that password or turning
its own login off. Authentik knows who they are; Uptime Kuma never does.

Uptime Kuma's built-in login can then be turned off under **Settings →
Security → Disable Auth**, which makes SSO seamless. That is a real trade:
Authentik becomes the only thing standing in front of the dashboard, so
anything reaching the Service directly inside the cluster gets in unchallenged.
Leaving it enabled costs a second login and removes that hole. There is no
environment variable for either choice, so it cannot be expressed here.

## Status pages

Forward auth covers the whole host, so public status pages under `/status/`
are behind the login too. Publishing one means excluding those paths from the
middleware — a second Ingress for the `/status/` prefix without the
`router.middlewares` annotation, pointing at the same Service. Not done here,
because nothing is published yet.
